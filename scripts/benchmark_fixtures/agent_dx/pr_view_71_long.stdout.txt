## Problem and behavior

Codex setup previously wrote MCP and instructions but did not install native lifecycle hooks. `hook codex` also attributed events and fresh session task IDs to Claude. Codex setup now writes project `.codex/hooks.json`, keeps user handlers and unknown events, and replaces only exactly generated Packet28 handlers. Hook files are bounded, reject symlinks, and use an atomic write with a retained directory lease.

Native Codex events now record Codex attribution, retain the original host command and permission policy, and use a separate fresh-session namespace while preserving explicit or active continuation task IDs. Hook execution does not bootstrap the Claude HTTP service. User MCP configuration honors `CODEX_HOME`; doctor checks the Codex user/project registration and all generated lifecycle handlers, exercises the local Codex adapter/MCP handoff, and reports host enablement, trust and execution as unverified. Doctor requires the same exact shell serializer as setup, including correct escaping of literal `$` paths.

Explicit successful Codex hook setup now re-enables Packet28 ingestion using the opt-in behavior already reviewed in #55. Configuration/token initialization alone still preserves a disabled state. The setup integration cases require all seven generated lifecycle events and the correct guarded Codex command/root.

This PR inherits final #70 head `720f4e216932bc096c2aded71f5d7368d16b015a`, including action-critic documentation, bounded GitHub PR previews and explicit benchmark compatibility. Explicit CLI/MCP reduction remains available. Setup still uses the existing generic hook-service bootstrap; this change does not claim that Codex setup starts no HTTP service.
